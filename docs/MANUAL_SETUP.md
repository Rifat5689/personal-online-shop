# Setup before production launch

1. Review the test storefront at https://test-originsofbeauty.web.app and its admin at `/secure/admin`. Demo login is autofilled. Confirm shipping rates, product stock/prices, images, contact information, order processing and mobile navigation.
2. Production is prepared under Firebase project `personalshop` and Azure app `originsofbeauty`. Its database and image container are separate from testing and Ownshop. The frontend remains unpublished until the manual launch workflow runs.
3. Replace the initial owner password securely in the production database before taking real orders; the copied admin settings do not include password management. Check the store's public support email, WhatsApp number and shipping policy. Rotate the MongoDB credential supplied during setup through Azure app settings when appropriate. Never commit credentials.
4. Confirm Azure app settings `MONGODB_URI`, `ACCESS_TOKEN_SECRET`, `REFRESH_TOKEN_SECRET`, `STORE_SLUG`, `CORS_ORIGIN`, `AZURE_STORAGE_ACCOUNT_NAME`, and `AZURE_STORAGE_CONTAINER`. Production uses `DATABASE_ROLE=primary`, `DB_MIRROR_ENABLED=true`, and `MONGODB_MIRROR_URI` pointing to the test database. Testing/localhost must keep mirroring disabled and use only the test database. Production CORS must include `https://originsofbeauty.web.app`; testing must include `https://test-originsofbeauty.web.app`. Both apps use `SCM_DO_BUILD_DURING_DEPLOYMENT=false` for prebuilt packages and `WEBSITES_CONTAINER_START_TIME_LIMIT=1800` to allow initial dependency extraction on the existing B1 plan. If a cancelled deployment leaves `DeploymentInProgress`, inspect Kudu processes and archive only confirmed stale deployment metadata before retrying; do not cancel and repeatedly restart active builds.
5. Azure deployment uses OIDC and repository variables `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, and `AZURE_SUBSCRIPTION_ID`. Its Website Contributor role is scoped to the two designated Azure apps. Firebase deployment uses repository-restricted Google workload identities. Neither provider needs publishing passwords or downloaded service-account keys. Keep Azure password-based SCM publishing disabled. Repository variable `DEPLOY_ENABLED=true` enables deployment jobs.
6. Merge the verified release from `develop` to `main`. In GitHub Actions, open **Deploy isolated shop**, select the `main` branch and `production`, then run the workflow. It deploys the production backend, builds without demo autofill, and publishes `originsofbeauty.web.app`.
7. Verify `/`, product details, cart/checkout, order tracking and `/secure/admin` on the production URL before taking real orders. Checkout uses cash on delivery; no online-payment integration was added.

Testing adds demo inventory; it is never promoted into the production database. Production changes are replicated to matching test records, preserving test-only records. This mixed testing database is a working backup, not a pristine restore point; retain independent MongoDB backups for recovery. Changes to the old Ownshop store after the initial copy are not automatically copied.
